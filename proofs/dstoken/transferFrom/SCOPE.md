# Verification scope: `DSToken.transferFrom`

## Program boundary

The verified entry computation is one fresh EVM message-call frame executing the exact 6,955-byte runtime image from `/app/contract.bin` with canonical ABI calldata for `transferFrom(address,address,uint256)`.  Its log substate starts empty, as at a fresh external transaction/call boundary.  The call frame is explicitly snapshotted before execution and completed through KEVM's `#return` continuation, so exceptional execution restores accounts and substate just as an external call does.  The theorem includes the dispatcher, Solidity 0.4-era non-payable check, `stoppable` modifier, anonymous `LogNote`, the base `DSTokenBase.transferFrom` implementation, its arithmetic assertions, its `Transfer` event, and ABI boolean return encoding.

The account executing the code is symbolic `TOKEN`; its deployed code is the supplied runtime image.  `TOKEN` is a 160-bit address other than Shanghai's precompile addresses 1 through 9; address zero remains covered because the pinned semantics does not classify it as a precompile.  The EVM fork is `SHANGHAI`, execution mode is `NORMAL`, gas accounting is disabled (`<useGas> false`) so the theorem is functional rather than a gas-availability theorem, and the call is non-static.  The outer caller state has call depth zero and empty call/world snapshot stacks; its word stack remains symbolic and receives the call-success flag.  Zero-value claims inject call value zero.  The non-payable claim injects a symbolic positive 256-bit call value; the omitted value-transfer prelude is observationally irrelevant because that branch reverts and the call snapshot is restored.

## Input domain

`SRC`, `DST`, `CALLER`, and `TOKEN` range over 160-bit addresses, with `TOKEN = 0` or `TOKEN > 9`. `WAD` and (for the non-payable case) `CALLVALUE` range over unsigned 256-bit integers. Calldata is exactly the canonical ABI encoding generated by `#abiCallData("transferFrom", #address(SRC), #address(DST), #uint256(WAD))`; malformed, short, trailing, or noncanonical calldata belongs to dispatcher behavior outside this function-call contract.

Storage is an otherwise arbitrary symbolic KEVM map.  The claims read Solidity's slot 1 mapping for `_balances`, slot 2 nested mapping for `_approvals`, and byte offset 20 of slot 4 for `stopped`, matching the supplied bytecode.  Relevant loaded words are constrained to unsigned 256-bit values.  Successful writes additionally assume the relevant hashed mapping locations are pairwise distinct and distinct from slot 4.  This is the conventional Solidity storage-layout non-collision assumption; KEVM models `keccak` without an injectivity theorem, and the real Solidity layout likewise depends on cryptographic collision resistance.  It is an explicit conditional trust boundary, not a restriction on address or amount values.

For zero call value, the claims partition implemented control flow into:

1. stopped (packed byte is nonzero): exceptional `INVALID`;
2. running but source balance below `WAD`: exceptional `INVALID`;
3. running with sufficient balance but allowance below `WAD`: exceptional `INVALID`;
4. running with sufficient balance and allowance, distinct source/destination, but destination addition overflows: exceptional `INVALID`;
5. successful distinct-address transfer with no overflow; and
6. successful self-transfer, for which the two sequential balance writes restore the original balance.

A seventh claim covers every positive call value and the dispatcher's `REVERT`, which occurs before the stopped/storage branches.

## Observable final state

The theorem observes:

- the callee status code and return-data buffer;
- the outer call's success flag left on the restored caller word stack;
- the complete token storage map (updated exactly on success and restored exactly on failure);
- the EVM substate log, initially empty at this fresh-call boundary (the anonymous `LogNote` followed by `Transfer` on success, empty/restored on failure);
- the exact runtime code of the token account; and
- KEVM call bookkeeping needed by the pinned semantics: caller/token become touched on every call, while accessed-account additions commit only on success because accessed accounts are inside the restored substate.

Caller VM state is restored by KEVM's call-stack mechanism.  Other accounts, untouched token-account fields, block/environment cells, accessed-storage bookkeeping, memory internals, program counter, and gas are framed because they are not part of the requested functional storage/result/event behavior; gas is disabled, so the explicitly constrained accessed/touched-account changes cannot influence an observed gas result.

## Intended property

For a canonical zero-value call while running, `transferFrom` succeeds exactly when the source balance and caller allowance cover `WAD` and the destination addition does not overflow (self-transfer cannot overflow after the prior subtraction).  Success returns ABI `true`, decrements the caller's allowance, moves the balance for distinct addresses or restores it for a self-transfer, preserves every other storage entry, and appends the exact note and transfer logs.  A stopped token, insufficient balance, insufficient allowance, or destination overflow reaches the compiler's `INVALID`; the enclosing message-call rollback restores storage and logs and returns call-success flag zero.  A positive call value reaches the non-payable `REVERT` with the same rollback and zero call-success flag.

## Chosen contract readings

- “The `transferFrom` function” means canonical ABI calls reaching selector `0x23b872dd`, including the inherited modifiers and base implementation actually present in the supplied runtime bytecode. Dispatcher behavior for malformed calldata or other selectors is excluded.
- “Successful and unsuccessful calls” means every implemented zero-value branch above plus the non-payable positive-value branch. Resource failures such as out-of-gas are excluded because gas accounting is intentionally disabled.
- Failure is observed at the external-message-call boundary, not at the raw intra-frame instant of `INVALID`; therefore earlier log/storage effects are rolled back, matching EVM call semantics.
- Events are observable implemented behavior. The anonymous note has four indexed topics (`msg.sig`, caller, first calldata word, second calldata word) and the supplied compiler's concrete data layout for `(msg.value, msg.data)`: zero value, offset 64, length 100, and the 100 canonical calldata bytes without a final 28-byte padding suffix. The successful transfer also emits the standard padded `Transfer` event.
- Solidity mapping-location non-collision is explicit and conditional, as described under Input domain. No program-defined code or arithmetic behavior is trusted or replaced.
